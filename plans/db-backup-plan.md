# План: резервное копирование Postgres

Составлен 2026-07-30. Закрывает пункт «Бэкапов нет вообще» из `mainnet-cutover-plan.md`
(фаза 0) — **делается ДО перехода на реальные деньги**.

## Решения (согласованы с владельцем 2026-07-30)

- **Основной внешний канал:** Cloudflare R2 (S3-совместимый, 10 ГБ бесплатно, без платы за трафик).
- **Частота:** дамп каждый час; каждый дамп сразу уходит в R2.
- **Дубль:** раз в сутки зашифрованный дамп телеграм-ботом в личку владельца.
- **Шифрование:** `age` с асимметричной парой ключей — на сервере лежит только
  **публичный** ключ (шифрование), приватный (расшифровка) хранится у владельца вне сервера.
  Утечка любого хранилища бэкапов без приватного ключа бесполезна.

## Схема

```
cron (хост, ежечасно, minute=17)
  └─ /opt/tg-poker/backup.sh
       1. docker compose exec -T postgres pg_dump -U poker -Fc poker_db
          → db-YYYYMMDD-HHMM.dump          (консистентный снапшот, app не останавливается)
       2. age -r <pubkey> → db-....dump.age (оригинал не сохраняется)
       3. локально: /opt/tg-poker/backups/, ретеншен 48 часов
       4. rclone copy → r2:tgp-backups/hourly/
       5. если час == 03 UTC:
            копия → r2:tgp-backups/daily/
            + sendDocument ботом в личку владельца
       6. любая ошибка шагов 1–5 → sendMessage ботом владельцу (алерт)
```

Ретеншен в R2 — lifecycle-правилами бакета (не скриптом):
`hourly/` — удалять через 7 дней; `daily/` — через 90 дней.

**Объёмы:** дамп сейчас < 5 МБ. Локально 48 × 5 МБ ≈ 250 МБ; в R2
(168 hourly + 90 daily) × 5 МБ ≈ 1.3 ГБ — в бесплатные 10 ГБ помещается с запасом.

## Шаги реализации

### 0. Входные данные от владельца
- [ ] Аккаунт Cloudflare → R2 → создать бакет `tgp-backups` → API-токен
      (Access Key ID + Secret Access Key + Account ID). Токен скоупить только на этот бакет.
- [ ] Telegram chat id владельца для дублей и алертов (получим через `getUpdates`
      после `/start` боту — вебхук на боте не настроен, конфликта нет).
- [ ] Решить, где живёт приватный ключ `age` (менеджер паролей; можно + бумажная копия).
      ⚠️ **Потеря приватного ключа = все бэкапы превращаются в мусор.**

### 1. Подготовка сервера (один раз)
- [ ] `apt install age` (или бинарь с GitHub), `curl https://rclone.org/install.sh | bash`.
- [ ] Сгенерировать пару: `age-keygen -o /root/tgp-backup.key`; **публичную** строку —
      в `/opt/tg-poker/.env` (`BACKUP_AGE_RECIPIENT=age1...`), файл с приватным ключом
      отдать владельцу и **удалить с сервера** (`shred -u`).
- [ ] `rclone config` → remote `r2` (type s3, provider Cloudflare); проверить
      `rclone lsd r2:tgp-backups`. Права: `chmod 600 ~/.config/rclone/rclone.conf`.
- [ ] В `.env` добавить `BACKUP_TG_CHAT_ID=<id>` (BOT_TOKEN там уже есть).
      Compose-списка это не касается — скрипт работает на хосте и читает `.env` сам.
- [ ] `mkdir -p /opt/tg-poker/backups && chmod 700 /opt/tg-poker/backups`.
- [ ] Каталог в `.gitignore` (репозиторий и есть `/opt/tg-poker` — иначе дампы
      всплывут в `git status`).

### 2. Скрипт `/opt/tg-poker/backup.sh` (в репозитории)
- [ ] Всё из схемы выше, плюс:
      `set -euo pipefail`; `flock` на lock-файл (защита от наложения запусков);
      лог в `/opt/tg-poker/backups/backup.log` (с ротацией по размеру);
      `trap` на ошибку → sendMessage-алерт с текстом упавшего шага;
      имя сервиса БД — `postgres` (не `db`).
- [ ] Проверка «дамп не пустой»: размер > 10 КБ до шифрования, иначе — ошибка
      (ловит сценарий «Postgres лежит, cron бодро бэкапит нули»).

### 3. Крон (хост)
- [ ] `/etc/cron.d/tgp-backup`: `17 * * * * root /opt/tg-poker/backup.sh >> ... 2>&1`.
      Минута 17 — чтобы не совпадать с деплоями и чужими «ровно в час» задачами.

### 4. Lifecycle-правила R2
- [ ] В консоли Cloudflare на бакете: `hourly/` → expire 7 days, `daily/` → expire 90 days.

### 5. Проверка восстановления (обязательная, до вычёркивания пункта из mainnet-плана)
- [ ] Скачать свежий `.age` с R2 **на другую машину** (локальную), расшифровать
      приватным ключом, поднять чистый `postgres:16-alpine`, `pg_restore -d poker_db`.
- [ ] Сверить: `count(*)` по `users` и `transactions`, сумма `balance`, последняя
      строка леджера — совпадают с продом на момент дампа.
- [ ] Записать фактическое время процедуры (это RTO) в этот файл.
- [ ] Повторять после крупных миграций схемы; иначе — раз в квартал.

### 6. Мониторинг тишины
- [ ] Алерт срабатывает при ошибке, но не при «cron вообще не запустился».
      Дешёвое решение: суточный ТГ-дубль и есть heartbeat — **нет утреннего файла
      в личке = бэкапы стоят**, разбираться. Зафиксировать это как договорённость
      (владелец «подписан» на утренний файл).

## Что сознательно НЕ делаем (и почему)

- **WAL-архивация / PITR / реплика** — на базе в мегабайты это инфраструктура ради
  инфраструктуры; почасовой дамп покрывает риск. Вернуться к вопросу, когда дамп
  перевалит за сотни МБ или час потерь станет недопустим.
- **Бэкап тома `pgdata` целиком** — `pg_dump` переносим между минорными версиями и
  восстанавливается выборочно; сырой том — нет.
- **Хранение нешифрованных дампов где-либо** — включая локальный каталог.

## Восстановление (шпаргалка на чёрный день)

```bash
# на новом/том же сервере, postgres поднят, база пустая
rclone copy r2:tgp-backups/hourly/<последний>.dump.age .
age -d -i tgp-backup.key <файл>.dump.age > restore.dump
docker compose -f docker-compose.prod.yml cp restore.dump postgres:/tmp/r.dump
docker compose -f docker-compose.prod.yml exec -T postgres \
  pg_restore -U poker -d poker_db --clean --if-exists /tmp/r.dump
# затем: сверить money invariant в админке; фишки за столами на момент дампа
# потеряны (жили в памяти) — инвариант покажет ровно этот разрыв.
```

⚠️ Нюанс восстановления: стеки сидевших игроков живут в памяти `TableManager`, в дампе
их нет — после восстановления инвариант покажет недостачу размером «фишки в игре на
момент дампа». Это ожидаемо; спорные случаи разбирать по `HandHistory` + session JSONL.
